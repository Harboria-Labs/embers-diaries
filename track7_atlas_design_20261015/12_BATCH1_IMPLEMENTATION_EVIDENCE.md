## Final consistency protocol

The existing WAL is retained. `store.json` is **not** a reliable committed generation: native record publication and COMMITTED WAL append precede its replacement (`rust/ember_core/src/lib.rs:671-710`), and WAL checkpoint removes committed frames. Batch 1 therefore adds one small `meta/source_epoch.json` **change epoch**, not a second WAL or index. Under Ember's shared store lock, the epoch is atomically advanced **before** a native record transaction, native WAL replay, native supersession sidecar or Python deprecation sidecar (`lib.rs:498-536,671-710,726-770,1051-1066`; `storage/store.py`; `engine/writer.py`). The older installed extension is supported through the same pre-change advancement in `PhysicalStore`/`WriteEngine`; the new native build advertises protocol version 1. An interrupted operation can leave the source epoch ahead, causing safe reconciliation. It cannot leave an acknowledged supported write hidden behind an equal indexed epoch.

`MasterIndex.persist(indexed_epoch)` atomically publishes the entire existing `master.json` with its applied epoch **after** index callback work; its in-memory applied epoch advances only after publication succeeds (`embers/index/master.py`). On every DB open, `EmberDB._reconcile_master_index` strictly reads authoritative physical records, checks record identity/integrity, sidecar consistency, repairs a uniquely inferable missing supersession sidecar, resets all MasterIndex postings, reindexes and publishes the current epoch (`embers/db.py`). An ambiguous or wrong sidecar fails closed. On a warm handle, a healthy MasterIndex-backed lookup reads only the small source epoch and uses its candidate metadata. If behind, it performs explicit source-backed reconciliation; it does **not** trust another process's derived snapshot or silently accept a false empty result. Conflict type/namespace candidate metadata has a separate in-memory seal, checked without physical directory enumeration; unexpected mutation fails closed. Equal epochs do not attest old physical bytes. Independent auditing remains Batch 3.

`conflict_records`, `conflicts_for` and `_find_live_conflict` now select CONFLICT IDs from that same MasterIndex, verify each used record and current head, retain ACL/status/history behavior, and never scan unrelated namespace record bodies on a healthy path (`embers/db.py`). Map pair lookup/write and status head/transition/update use the shared store lock; status updates pass the existing `expected_hash` CAS. General memory updates still permit intentional branching. An idempotent map retry repairs a graph edge absent after a committed record but interrupted graph link, without treating graph edges as conflict authority.

## Compatibility, recovery and rollback

- This local implementation assumes writes enter the new `PhysicalStore`/`WriteEngine` or staged native transaction APIs under the shared lock. A separately running **old Python writer** does not advance the new epoch. Do not mix old and new writers against one store during deployment; coordinate the runtime upgrade and perform an initial source-backed certification. Raw native callers must also hold Ember's store lock for cross-process epoch serialization.
- The new native transaction/recovery/supersession functions advance the same epoch before source changes. Current tests prove isolated process interruption and restart, not power-loss durability or live binary compatibility. Staged source/native behavior and old-extension compatibility were tested separately.
- Initial certification is a full strict source scan. Healthy lookups do not enumerate filenames or unrelated record bodies. Any behind epoch, malformed relevant conflict, ambiguous sidecar or in-memory candidate corruption causes explicit reconciliation or failure. Out-of-band changes to old physical bytes with unchanged epoch remain an independent-audit matter.
- Rollback before deployment: restore the five changed runtime source files and Rust source from the pre-Batch-1 snapshot, and omit the new Batch 1 test file; no production data migration or deletion is needed because only temporary stores were written. For a store ever opened by the new code, preserve immutable records/WAL/sidecars and rebuild the old derived MasterIndex from source before trusting an older reader. Do not delete source records or sidecars.
