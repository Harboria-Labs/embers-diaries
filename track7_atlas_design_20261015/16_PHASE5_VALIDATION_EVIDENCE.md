### Fingerprint call path and work type

`EmberDB.conflicts_for` → `conflict_records` → `MasterIndex.get_type_ids` → `ensure_current` → `EmberDB._ensure_master_index_current` reads the small `source_epoch.json` marker under the store lock. With equal epochs it returns without physical reconciliation; `get_type_ids` then calls `_candidate_fingerprint()` on **every** request. That function sorts all in-memory record `(id, namespace, type)` rows and namespace posting sets, hashes their representation, then the query filters its namespace/type candidates. `promotion_route` reaches the same path through its mapped-conflict check. Lexical recall does not call this fingerprint. `MasterIndex.persist` also fingerprints after writes; a cold `MasterIndex._load` and `EmberDB._reconcile_master_index` do so during initialization. A behind epoch triggers `_reconcile_master_index`, which enumerates and strictly reads all physical records before persisting a new candidate seal. Explicit reconciliation does the same scan. The in-memory seal is a deliberate fail-closed check against unexpected posting edits; `test_in_memory_wrong_type_candidate_fails_closed` depends on it.

The pure fingerprint CPU probe repeated the metadata hash **1,000 times** per tier to resolve Windows' coarse per-call process CPU clock. At 55/155/305 rows, total process CPU was **125.000/359.375/734.375 ms**, or about **0.125/0.359/0.734 ms per hash**. The corresponding 1,000-call wall times were **128.141/364.377/1316.308 ms**. Per-request fingerprint wall medians within `conflicts_for` were **0.162/0.398/1.513 ms**; other work and machine noise dominate end-to-end latency. The per-call `process_time_ns` samples in the raw file quantize at about 15.625 ms and should not be interpreted individually. These are local CPU measurements, not a complexity proof or production capacity estimate.

At 305 records, a second handle's cold open took **720.385 ms**, with 1 physical-ID enumeration, 305 strict reads, 1 reconciliation and 2 fingerprint calls over 610 total rows. A healthy conflict lookup took **16.551 ms**, with 5 physical reads, 0 enumerations, 0 reconciliations and 1 fingerprint over 305 rows. After an actual independent child process wrote one record, the parent's first lookup took **412.474 ms**, with 1 enumeration, 311 physical reads (306 certification plus 5 query reads), 1 reconciliation and 2 fingerprints over 612 rows. The following healthy lookup took **20.259 ms**, 5 reads and 1 fingerprint over 306 rows. Explicit reconciliation took **365.382 ms**, 1 enumeration, 306 strict reads and 1 fingerprint. These are single event timings; the count boundaries are also asserted in `test_fingerprint_runs_on_healthy_lookup_and_physical_scan_is_epoch_gated` using two handles.

### Contract verdict

The growth is **in-memory metadata iteration and CPU work on every healthy conflict type lookup**, not unrelated physical record reads or physical directory scans. Batch 1's approved evidence explicitly disclosed this per-query candidate-seal iteration and claimed bounded physical I/O, not constant total time. The observation therefore does **not** demonstrate a violation of the approved Track 7 contract. No index architecture or runtime source was changed. Any future request for bounded total query CPU would need a separately approved integrity contract: removing the seal call alone would weaken the demonstrated fail-closed in-memory wrong-type detection.
