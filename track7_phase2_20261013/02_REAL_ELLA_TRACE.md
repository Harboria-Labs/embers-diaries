# Authenticated persisted path

The benchmark uses `AgentRegistry.register` and `authenticate` (`embers/identity/registry.py:39-81`) against a fresh `EmberDB.connect` store, creates a private namespace owned by the registered agent, and authenticates again before each write. It calls `MemoryProtocol.remember` (`embers/integration/memory_protocol.py:103+`) for a durable DOCUMENT claim, then `EmberDB.attach_evidence` (`embers/db.py:1677+`) for five distinct evidence records with separate references and source identities. The five evidence records are reused by later distinct assessment/request identities; repeated assessment of one source is not treated as independent truth.

For each report, `EpistemicLedger.apply` (`embers/cognitive/epistemic.py:103-340`) checks namespace write access, validates request ID and expected revision, calls `load`, checks the exact target hash, resolves available evidence, validates evidence integrity, builds a new assessment, and projects before/after state to enforce confirmation crossing. It validates the next state and response, embeds the full next state and response in an event, asks native `ella_reduce` to validate the transition, seals the event, and passes an immutable RAW record to `WriteEngine.write`.

`EpistemicLedger.load` (`epistemic.py:25-40`) enumerates all store IDs, sorts matching journal IDs, reads each record, checks type/namespace/sequence, verifies the record a second time, checks the chain seal, then replays every event with native `ella_reduce`. `EmberStore.read` (`storage/store.py:260-278`) already verifies sealed records. Thus exactly two integrity checks per journal record were counted during isolated loads: 50 reads and 100 verifications at 50 events.

`EmberStore.write` (`storage/store.py:194-239`) uses the installed native `write_record_transaction` path, which appends pending and committed WAL entries and durably publishes the immutable record (`rust/ember_core/src/lib.rs:640-668`). After record commit, `EpistemicLedger.apply` calls `observation_journal.initialize` and `append` (`integration/observation_journal.py:15-58`), which inserts a durable SQLite observation. `committed` wakes listeners. This isolated DB did not call the optional `write_observation.install`, so its extra source-sync path was not part of this fixture.

Projection (`epistemic.py:49-101`) reads the target, retrieves the five evidence records, reconstructs them, asks `db.conflicts_for`, calls native `ella_project`, and adds confirmation/lifecycle metadata. `db.conflicts_for` (`db.py:931+`) calls `conflict_records` (`db.py:903+`), which requests every namespace record through `ReadEngine.get_namespace` (`engine/reader.py:126+`) and filters for conflicts afterward. In this fixture that includes the ELLA RAW records although there were zero conflicts. This is source-verified and was measured in `projection_profile.csv`.

The correction used the authenticated `correct_evidence` action after 50 reports. It added an ELLA override for the first evidence reference. The underlying evidence record remained byte-for-byte semantically unchanged (`to_dict` equality), and the reopened ledger reconstructed the identical ELLA state.
