# Execution paths

Each row gives initiating surface → calls → read/write effects → result and failure boundary. Line references are in [validation references](VALIDATION_REFERENCES.md). The MCP server's installed surface wrappers and REST adapters are transport entry points; the called domain implementation is shared where indicated.

| Operation | Initiation and calls | Reads / writes | Result / failure |
|---|---|---|---|
| Memory creation | SDK `MemoryProtocol.remember`, REST `/v1/memory/write`, MCP `ember_write` → `EmberDB.write` → `WriteEngine.write` → `PhysicalStore.write`; optional embedding/context write validation; callback `_index_record` | Writes sealed immutable record via native transaction or WAL, then index views and optional write-observation receipt | ID; validation, quota, integrity, duplicate ID, namespace/agent ACL errors surface; observer delivery can recover after commit |
| Ordinary recall | REST `/v1/memory/recall`, MCP `ember_recall`, SDK `MemoryProtocol.recall` → text/vector query → decay ranking → `ContextBuilder`; optional `pairing.select` | Reads indexes and selected records; records access sidecar for direct rows; optional Pairing reads graph/FUR; selected public records may request ELLA summary | Text/messages/structured/raw or inspection envelope; no match returns empty context; optional ELLA summary failure is flagged on public memory reads, dedicated ELLA reads raise |

| Pairing | Ordinary or research recall → `integration/pairing.select` → outgoing edges of first admitted direct ID → native `pair_select` with FUR W → record availability → caller's capacity gate | Reads graph, FUR state, candidate record; selection itself writes nothing; `pairing.link` writes graph edge | One candidate/provenance or none; no second-best substitution after availability/admission failure; direct result order preserved |

| Agent auth | REST `/v1/agents/register` or MCP `ember_register` → `AgentRegistry`; later token auth + namespace ACL/session gate | Registry writes agent identity/hash; authenticated calls check token, namespace and own active session when required | ID/token on registration, authorized operation or explicit auth/access error |

Failure behavior also depends on transport adaptation: `EmberMCP.call_tool` converts domain exceptions to tool errors (`embers/mcp/server.py:132-153`); FastAPI routes translate selected exceptions to HTTP errors. Raw SDK callers receive Python exceptions.

## Reconciled existing paths — 2026-10-15

- **Physical commit/recovery:** native record transaction appends WAL PENDING, atomically publishes immutable record, appends COMMITTED, then replaces store metadata; startup recovers pending record entries (`rust/ember_core/src/lib.rs:641-738`). Supersession sidecar and MasterIndex callback occur later in `WriteEngine.update` (`embers/engine/writer.py:225-259`), so WAL recovery does not certify every derived view.
- **Memory versus ELLA versus conflict concurrency:** memory `update(expected_hash)` performs head-hash CAS under the shared store lock, while omission deliberately allows branches (`writer.py:98-176`); ELLA `apply` uses request-id idempotency and expected journal revision under that lock (`epistemic.py:96-113`); conflict status transition currently calls `update` without expected hash after separate head validation (`db.py:961-1000`).
- **Admission/review:** proposal `submit` routes through Automatic/Consensus/Human/Hybrid policy and either HOLDs or calls `db.promote`; explicit human promotion uses the same durable proposal/memory path (`promotion.py:141-321`; `db.py:1429-1550`). Conflict open queue/status review is a distinct record lifecycle (`integration/conflict_protocol.py:14-96`). `audit_write` reads one write's lineage/provenance; physical verification and maintenance are separate (`db.py:443-560`; `storage/store.py:260-275`; `maintenance.py`).

## Batch 1 local execution paths — 2026-10-16

- **Commit/index:** `PhysicalStore.write` under shared lock → source epoch advanced before native PENDING/record/COMMITTED → `WriteEngine._notify` → `EmberDB._on_write` → existing index updates → atomic `MasterIndex.persist(indexed_epoch)`. New native transaction/recovery/supersession functions advance the same epoch; the installed old extension uses Python advancement. Callback failure leaves source durable and epoch ahead, so indexed reads reconcile. A deprecation sidecar advances epoch before write; DB then marks/persists MasterIndex under the lock (`storage/store.py`, `engine/writer.py`, `db.py`, `index/master.py`, native `lib.rs`).
- **Open/recovery/lookup:** store WAL recovery under shared lock → strict physical record/sidecar reconciliation and MasterIndex reset/rebuild → persisted applied epoch. A healthy MasterIndex-backed query compares epoch without filename enumeration. A behind handle reconciles from source; an in-memory type/namespace seal failure raises. The initial/open and behind scans are recovery work, not routine query audit.
- **Conflict:** REST/MCP shared protocol → `conflicts_for`/open queue → certified MasterIndex CONFLICT type candidates → selected sealed conflict/current-head reads and ACL/status filtering. Mapping locks pair lookup and write; status transition locks head validation and `update(expected_hash=...)`. An idempotent mapping retry repairs a missing graph edge after an interrupted map. Graph remains a relation, CONFLICT records remain status authority.

The older rows above describe the pre-Batch-1 snapshot. Exact isolated validation and limits are in `track7_atlas_design_20261015/12_BATCH1_IMPLEMENTATION_EVIDENCE.md`.

## Batch 2 promotion path — 2026-10-17

REST/MCP authenticated route or submit -> PromotionEngine._route_locked under the shared store lock -> verified proposal and derivation reads -> conflicts_for(include_closed=True, caller=actor) for current mapped CONFLICT heads -> status/winner and unmapped graph-hint evaluation. HOLD writes nothing. PROMOTE -> EmberDB._promote_locked rechecks ACL and conflict under the lock -> writes/reuses deterministic NODE and EVIDENCE -> updates proposal head with expected_hash CAS. Direct Human promotion uses the same final conflict recheck. Rejection uses the lock and proposal CAS. Integrity, permission, stale head and inconsistent retry errors surface. The multi-record promotion is retryable at tested interruption points but is not one native atomic transaction.
## Batch 3 integrity audit path — 2026-10-17

Authenticated REST POST or MCP `ember_integrity_audit` validates a nonempty namespace list and WRITE ACL for the complete scope; `run_integrity_audit` records a running report and active marker, enumerates physical `.ember` files independently of MasterIndex, checks scoped record identity/codec/hash/metadata/lineage/sidecars, compares persisted MasterIndex and source epochs, and atomically publishes complete, stale or failed status. REST uses a worker thread. GET or MCP status requires READ ACL for the entire stored scope; a lease-expired running report becomes interrupted. A local trusted caller can separately invoke `recover_master_index` only for a complete audit whose findings are exclusively derived-index drift; it invokes existing `_reconcile_master_index`, records the action and re-audits. Source corruption blocks repair. Ordinary memory/conflict reads never call this scan. See `tests/test_track7_batch3.py` and `14_BATCH3_IMPLEMENTATION_EVIDENCE.md`.
