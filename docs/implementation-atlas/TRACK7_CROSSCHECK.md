# Track 7 cross-check against implemented source

| Research question or prior recommendation | Source result and implication |
|---|---|
| How is ELLA state stored? | `EpistemicLedger.apply` writes immutable RAW events with the full post-event `state`, `response`, action, payload, revision, actor, request ID and hash-chain seal (`embers/cognitive/epistemic.py:275-286`). State includes assessments, evidence overrides, hard groups, policy and carried evidence (`:37,112-113,223-270`). It is persisted *inside journal events*, not a separate reusable projection. |
| Is incremental ELLA state already available? | `project(rid,state=...)` accepts an in-call state, and `apply` uses a copied next state, so **within-call** reuse exists (`:49-53,112-113,272-283`). But `read()` calls `project()` without state; each `apply()` starts with `load()`; `load()` rereads and reduces every event (`:25-40,92-104`). No durable independently verified ELLA checkpoint or same-object cache was found. A blanket claim that ELLA has no state reuse would be wrong. |
| Why replay history? | `load()` verifies sequence, record seals and event chain, seeds policy and calls native `ella_reduce` for every event (`:25-40`). Native reduction validates committed/replayed transitions (`rust/ember_core/src/domain/ella.rs`, `mod.rs:59-110`). The current code chooses full reconstruction for correctness and does not use the embedded latest state as a trusted shortcut. Prior research measured diskless replay, not complete persisted `apply` latency (`track7_research_20261013/01_EXECUTIVE_SUMMARY.md`, `08_LIMITATIONS.md`). |
| Can memory history substitute? | No without changing meaning. `get_history` follows `superseded_by` memory versions (`embers/engine/reader.py:81-96`), while ELLA journal contains evidence-specific assessments, corrections, merge/split, carry-forward, decision authority, CAS and retry identity. Existing history APIs help agents inspect claim versions and provenance, but do not validate or materialize the ELLA event state. |
| What lookup already exists? | `EmberDB.conflicts_for` is an authoritative **value** lookup over current CONFLICT records (`embers/db.py:903-959`), so “no conflict-specific lookup” is false. It is not a narrow index: it reads every current record in the namespace before filtering type (`embers/engine/reader.py:126-164`). MasterIndex has namespace/type metadata (`embers/index/master.py:98-159`), and the graph has `CONTRADICTS` relations (`embers/db.py:760-787`), but neither is alone authoritative for mapped status. |
| Can MasterIndex metadata replace the scan? | A healthy-index prefilter can reduce record reads, but is not proven equivalent. Master rebuild occurs only when empty (`embers/db.py:175-187`); stale nonempty type metadata can miss a conflict, and skipping an unrelated corrupt record changes observed error behavior. The Phase 3 counterexamples remain valid as research evidence (`track7_phase3_20261013/01_FINDINGS.md`, `05_COUNTEREXAMPLES.md`). Thus this is an **integration/contract question**, not proof a new persistent index is needed. |
| What maintenance/integrity already exists? | Record/evidence hash verification, native transaction/WAL recovery, index checkpoint, observation mirror recovery and maintenance cycle exist (`embers/core/record.py:210-231`, `embers/storage/store.py:169-192`, `embers/db.py:1901-1909`, `embers/integration/observation_journal.py:62-84`, `embers/maintenance.py`). None is an independently validated ELLA projection checkpoint. A whole-store integrity scan or certified index-health gate was not found. |
| Which bounded mechanisms already exist? | Native LADC activation/admission and context-scoped state, result/token caps, Pairing at most one expansion, physical quotas, observer page caps, and FUR same-object incremental reduction are implemented. They address distinct limits and do not solve ELLA replay automatically (`embers/integration/consolidated.py:52-147`, `embers/cognitive/usefulness.py:73-91`, `rust/ember_core/src/domain/dynamics.rs`, `pairing.rs`, `rust/ember_core/src/quota.rs`). |

## Reconciliation of Phases 1–4

- Phase 1's replay concern is supported by current source. Its diskless timing claims stay fixture-specific. Phase 2 subsequently measured a real isolated persisted 50-report sequence: last-five append median 1,929 ms, repeated load 469 ms and full projection 834 ms at 50 reports (`track7_phase2_20261013/01_FINDINGS.md`). This audit did not repeat it or establish production capacity.
- Phase 2's “incremental FUR versus full ELLA replay” distinction is supported, with the qualification that fresh FUR objects replay and reused ones still enumerate IDs/pass event identity summaries (`embers/cognitive/usefulness.py:73-91,119-129`).
- Phase 3 established that conflict lookup already exists and that naive type/graph prefilters change behavior. Its recommendation needs an explicit integrity/index contract before implementation.
- Phase 4's index/integrity contract remains open; `docs/consolidated-release-report.md:42-50` says the phase was recorded in a research transcript without a separate report. Any proposal to add a new history, conflict index, or maintenance mechanism should first state why existing version history, MasterIndex, conflict records, WAL and observation recovery cannot satisfy its exact semantics. This audit found no source proof that a new feature is required for conflict lookup; a durable verified ELLA projection remains genuinely absent.

The smallest next research action is to specify the exact observable integrity and index-health contract for `conflicts_for`, then write an equivalence matrix for any narrower integration. Keep ELLA checkpoint design separate until its replay equivalence criteria are established; the isolated persisted measurement is a baseline, not a correctness proof for a checkpoint.

## Focused design update — 2026-10-15 (research only)

The existing MasterIndex is the preferred **candidate** source because it already records namespace/type and lineage metadata (`embers/index/master.py:98-159`), but it is not currently a certified completeness source: physical writes commit before derived callbacks, callback failures are warnings, and a nonempty stale snapshot is not rebuilt (`embers/engine/writer.py:64-96`; `embers/db.py:175-187`). A narrow conflict query therefore requires an index health/generation gate and explicit rebuild/recovery. Conflict records and status versions remain authoritative; tags and graph links cannot replace them. The frozen boundary assigns unrelated-record verification to independent maintenance, while records returned/used by a query retain physical integrity checks.

Existing maintenance runs reflect/consolidate, and checkpoint persists indexes/WAL; neither is a strict, independent namespace-wide audit (`embers/maintenance.py`; `embers/db.py:1901-1909`). The proposed audit belongs in that existing lifecycle but needs strict decode, durable status and recovery reporting. `PhysicalStore.read` currently hides non-hash decode failures as `None` (`embers/storage/store.py:260-275`), so it cannot alone provide complete failure classification.

ELLA's last event already embeds the full next state, but verification of only that event cannot prove its earlier chain/reducer history (`embers/cognitive/epistemic.py:25-40,275-286`; `rust/ember_core/src/domain/ella.rs:236-245`). A verified per-process state seeded by replay and advanced through new native reductions is the smallest proposed acceleration; a durable projection is not established as necessary. Memory-version history remains separate from this journal. Detailed unimplemented designs and unresolved proof obligations are in `track7_atlas_design_20261015/`.

REST creates a new `EpistemicLedger` for each read/write request (`embers/api/research_routes.py:57-67`), so cross-operation reuse must live at a store/namespace or DB-service scope and still detect writes from other handles/processes. An instance-only cache would not solve the measured path.

## Reconciliation correction — 2026-10-15

Existing native WAL transaction/recovery protects physical source records; native atomic supersession sidecars, shared store locking, memory CAS, immutable history and `audit_write` already provide important correctness and provenance mechanisms. They do **not** make the separately maintained MasterIndex snapshot complete after every committed write (`embers/storage/store.py:83-114,163-275`; `rust/ember_core/src/lib.rs:641-738,1016-1069`; `embers/engine/writer.py:64-96,98-259`; `embers/db.py:443-560`). A new WAL or history system is not justified. The prior design's durable generation marker is a candidate only; existing physical-ID enumeration, reconciliation and rebuild must be evaluated first.

Promotion already has Automatic, Consensus, Human and Hybrid admission routes and pending human holds (`embers/engine/promotion.py:141-321`), while the Conflict Engine has explicit mapping, open queue and status review (`embers/db.py:789-1000`; `embers/integration/conflict_protocol.py`). These do not replace an independent physical audit. For ELLA, the smallest proposed experiment is store/namespace scoped disposable state reuse with existing `all_ids()`, lock, sealed events and native reducer, while retaining full replay for restart/recovery and a defined historical-integrity boundary. Detailed evidence and limits: `track7_atlas_design_20261015/08_EXISTING_MECHANISM_RECONCILIATION.md`.

## Upgrade-contract correction — 2026-10-15

The seven-upgrade [roadmap](../../track7_atlas_design_20261015/09_COMPLETE_UPGRADE_ROADMAP.md) now makes MasterIndex trust a prerequisite for narrow conflict retrieval and conflict concurrency. A physical-ID comparison detects missed/new commits, but **cannot** by itself detect same-ID wrong type/namespace, sidecar-only deprecation, or old-byte tampering. The proposed open-time source reconciliation, warm sidecar/ID health checks, and explicit fail/rebuild path remain **unimplemented** and require tests. `MasterIndex.index_record` overwrites its record row without removing old namespace/tag postings, so a stale snapshot must be reset/rebuilt rather than incrementally overwritten (`embers/index/master.py:57-159`).

Promotion status outcomes beyond OPEN/INVESTIGATING, audit authority/retention, and the ELLA old-event tamper boundary remain user-policy decisions (`11_REUSE_AND_POLICY_DECISIONS.md`). A store/namespace scoped disposable ELLA cache can reuse full replay at cold start and native reduction for new events, but no warm cache can claim immediate detection of arbitrary old-event byte edits from journal IDs alone. The roadmap and tests are design requirements, not implemented capabilities or validation evidence.
## Batch 4 reconciliation — 2026-10-17

The original V1 answers above remain historical. Current local candidate `EpistemicLedger.load()` still replays all sealed events as source truth, while normal `read/project/apply` use a bounded process projection after a verified replay. Batch 1 source epochs detect supported cross-process writes; the known head and new events are strictly verified and reduced with unchanged native semantics; Batch 3 audit marker changes force replay. Agent-accessible memory-version history is still separate from ELLA's assessment journal. Old-event out-of-band tampering with unchanged epoch/head is detected by independent audit or explicit replay, not on every healthy warm request. See `15_BATCH4_IMPLEMENTATION_EVIDENCE.md`.
